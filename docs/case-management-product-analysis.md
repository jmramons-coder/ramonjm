## Recommended story

**Working title:** Keep the work connected. Make the decision explicit.

**Descriptor:** A working design and validation platform for insurance service work.

> Insurance work moves through requests, tasks, requirements and decisions. This workspace connects those records so a caseworker can see what is ready, what is holding the case up and the evidence behind the next decision. Configurable workflows provide the structure; contextual assistance helps explain the work; the person records the outcome and why.

The strongest spine is **request → configured work → dependencies and evidence → contextual assistance → human decision with a recorded reason**. Show the product doing work rather than narrating a dashboard inventory. Preserving orientation, making blockers legible and keeping decisions explicit are design intentions; no measured handling-time improvement, adoption, production launch, completed research program or certification is established here.

This is a database-backed demo/validation build, not a fixture-only frontend. Core records and mutations use Supabase. There are also browser-local compatibility paths, authored scenarios and simulated external systems. Current code is the authority where README/planning documents drift.

## Narrative and visual sequence

1. **Begin with a caseworker's next task.** A task queue and selected record explain ownership and why the work is actionable. Use an observed demo profile. Do not infer the portfolio author's role, team or duration from repository authorship.
2. **Reveal the structure behind the task.** Connect a request to configured stages, tasks, actions and requirements. Distinguish an action's outcome from task completion. Explain a blocking relationship rather than treating all status chips as equivalent.
3. **Keep related work within reach.** Open a task, requirement and document in the shared side panel. Recent contexts and back navigation support returning to related work. The implemented recent-history cap is six within the session; tab visibility is configurable and needs runtime confirmation.
4. **Explain what arrived before showing a wall of document.** The requirement panel puts findings or a human note above a bounded received-document preview. Findings retain verdict, actor, timestamp and a link to a follow-on requirement. Scenario-authored findings demonstrate this review pattern; they do not establish automated extraction accuracy.
5. **Make assistance inspectable.** The model-backed assistant receives bounded work context and read-only tools. Keep it distinct from deterministic inline recommendations and scenario-authored findings, even when all share AI visual treatment.
6. **End with an honest decision record.** The decision panel keeps the case visible, explains unresolved work, requires an outcome and reason, and closes only the decision task. Deciding early does not manufacture a completed work history.

A complex new-business underwriting/buy-sell scenario is authored in this repository. It demonstrates workflow depth, not production delivery of every scenario rule. Keep customer-specific medical, financial, legal ownership and dataset requirements out of public explanatory copy. `docs/import/request-types/tower-opportunity-profile.md:92–96` records historical scenario contradictions; do not silently combine older versions or assert a particular ownership arrangement.

The current conversational assistant is **Galia** (`src/app/features/assistant/lib/agents.ts:4–10,57–70`). Its persisted internal key remains `alex` for stored-turn compatibility; that is not its display name. Use Galia in current captions. ## Portfolio assistant and global queues — 26 October 2026

The public reconstruction now uses the same fictional records for queues, record panels and assistant replies. It follows the source assistant’s summary, next-step, blockers, requirements, documents, people, timing, automation and policy-file patterns, reviewed in `features/assistant/lib/respond.ts`, `capabilities/case-*.ts`, `lib/blocks.ts`, `model/tool-catalog.ts`, `lib/case-file.ts` and `supabase/functions/assistant/prompts.ts`.

Replies are deterministic in the portfolio: no model, source tenant, database or customer record is queried. Policy answers show only the authored policy number, insured, request and type. File answers distinguish received metadata from file contents; unsupported questions and mutation requests are explicit about that boundary. Linked cards open the matching case’s task, requirement, document or overview, retaining the existing contextual tab stack and separate conversation per case. Fresh answers include the action outcome selected in the local demonstration, without treating it as task completion.

Cases and Tasks are separate modules. My cases is the initial page. My tasks is based on task assignee across all five authored cases, independent of the case-owner scope. Both modules retain All/My tabs, shared table styles and search; task creation is disabled. Case-specific human assignments and due dates come from a shared task fixture, so the queue, record header and assistant agree. These are authored workflow examples, not a claim that all source cases share identical work.

Verification includes durable assistant tests for grounding, valid contextual targets, isolation, unsupported questions, read-only behavior, current action status and empty sources, plus the existing panel-state tests.
